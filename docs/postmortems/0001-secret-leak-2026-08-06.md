# Postmortem: Secret Leak via `Axonity-AI/.github` — 2026-08-06

**Status:** Resolved. **Severity:** High (real, active API keys exposed on a public repo). **Author:** written during the incident response itself.

This is a blameless postmortem: the goal is identifying the process gap that let this happen, not assigning fault. The mistake (committing a `.env` file) is exactly the kind every engineer makes at some point — the question that matters is why nothing caught it before or after it was pushed.

## What happened

`portfolio_projects` (later renamed to `Axonity-AI/.github`, the org's public profile repo) was made public as part of setting up an org homepage. Its git history — dating back to its very first commit, years earlier — contained a committed `chatbot/.env` file with real credentials. Making the repo public exposed that entire history, including the long-dormant secrets. GitGuardian (a third-party secret-scanning service monitoring public GitHub activity) detected and emailed two alerts within minutes of the repo going public: a "Claude API Key" and a "Generic High Entropy Secret."

## Timeline (2026-08-06, UTC)

- Repo renamed `portfolio_projects` → `.github`, visibility set to public.
- **~02:28** — GitGuardian scans the newly-public repo, detects two exposed secrets, emails alerts.
- User forwards both alerts immediately.
- Repo visibility reverted to **private** as the first action, within minutes of the alert — stops further public scraping.
- Full git history searched for secret patterns; `chatbot/.env` identified as the source, committed in the repo's first two commits (`6675c8d "Chatbot first commit"`, `4b3a29f "restart chatbot"`).
- Investigation found **five** real secrets in that one file — GitGuardian's two alerts were only the ones it had high-confidence detectors for:
  - `ANTHROPIC_API_KEY` (the flagged "Claude API Key")
  - `OPENAI_API_KEY` (likely the flagged "Generic High Entropy Secret")
  - `SECRET_KEY` (JWT signing secret)
  - `DATABASE__PASSWORD` (Postgres)
  - `REDIS_PASSWORD`
- A parallel check of `axonity_chatbot` (a separate, still-private repo) found its own independent leak: a real `OPENAI_API_KEY` committed in `backend/.env` across six commits, still tracked on the active `phase_3` branch at the time of the check.
- User rotated all five secrets from the `.github` incident (confirmed complete).
- `.github`'s history rewritten via `git filter-repo` to remove `chatbot/.env` from every commit; verified zero remaining matches for either leaked key string across full rewritten history; force-pushed; local clones resynced to the clean history.
- Repo re-verified clean (broader sweep for any other credential-shaped strings — none found beyond template placeholders) and made public again.
- Separately and independently, the same remediation pattern (rotate, scrub history, gitignore) was applied to `axonity_chatbot`'s `backend/.env` leak.

## Root cause

No layer in the pipeline was capable of catching a committed secret, at any point:

1. **No pre-commit secret scanning** — nothing stopped the original `git commit` of `chatbot/.env` from succeeding, years ago.
2. **No GitHub secret scanning / push protection enabled** — even after today's incident, checking repo settings confirmed `secret_scanning: disabled` on `.github` despite it being a public-eligible-for-free-scanning repo. It was never turned on.
3. **History treated as disposable** — the file was later removed from the working tree in a subsequent commit, which gave a false sense of "handled" without anyone checking that git history is permanent by default.
4. **Visibility change as the trigger** — the secret was harmless as long as the repo stayed private (private-repo secrets are still bad practice, but have a much smaller blast radius). The actual exposure event was the visibility flip to public, done without first auditing history for exactly this class of risk.

## Blast radius

Both keys were live in a public repo for a window of likely single-digit minutes before being caught and reverted (exact duration not logged, but immediate action was taken on alert). Public GitHub repos are scraped by automated bots within seconds of becoming public, so **both keys were treated as compromised regardless of the short window** and rotated — this is the correct default assumption, not an overreaction.

## Corrective actions (all completed)

- [x] Repo reverted to private immediately on alert.
- [x] All five exposed secrets identified and rotated by the account owner.
- [x] `chatbot/.env` purged from `.github`'s full git history via `git filter-repo`; force-pushed; verified with a zero-hit grep across all rewritten history.
- [x] Local clones resynced to match the scrubbed remote history.
- [x] Independently-discovered leak in `axonity_chatbot` rotated and scrubbed using the same pattern.
- [x] Full Axonity Engineering Standards program written (`ENGINEERING_STANDARDS.md`, `REFACTOR_GUIDE.md`) with §5 (Secret management) directly derived from this incident.

## Prevention (why this shouldn't happen again)

- **Pre-commit secret scanning** (`.pre-commit-config.yaml`, gitleaks/detect-secrets hook) — the earliest possible catch, before a secret ever reaches even local git history, let alone GitHub.
- **GitHub secret scanning + push protection** enabled on every repo (free on public repos; requires GitHub Team/Advanced Security on private ones — see `ENGINEERING_STANDARDS.md` §11) — a second line of defense that rejects the push itself if a known secret pattern is detected.
- **Standing policy**: any repo visibility change (private → public) requires a history audit for secrets *first*, not after an alert forces it.
- **Standing policy**: a secret is compromised the moment it's pushed to any repo, private or public, past or present tense — rotate on discovery, don't assess "was it really exposed."
